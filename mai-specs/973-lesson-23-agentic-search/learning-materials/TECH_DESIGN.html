1. 交付范围与现有实现的调整

本课补齐知识库检索，让主 Agent 在通用 Loop 中按缺口查找和验证，并通过统一入口交付普通回答或循证回答。

2026-11-22 · 实现与验收核对版。 通用检查点、final_answer、知识库首次调用固定资料及显式正文路由已接入。真实 Chat、自动检查和业务验收分别记录，历史用例保留原结论。

建设内容 这版的决定
知识库 保留 Web 管理、索引、搜索和原文读取；在工具首次调用时固定可用资料
Agentic Search 默认使用任务适用的搜索方法；复用主 Agent 循环，保留代码执行、MCP 与子 Agent
Verify 工具批次返回后登记结果，候选交付前检查完整性；问题回流到同一 Loop
回答 一个 final_answer 工具，plain / evidence 两种模式；校验通过后发布正文
权限 工具与来源服务负责当前用户权限；无库、无匹配、拒绝与故障分别反馈

普通 Chat 已验证概念解释的 plain 路由、正式指标 180,840.20 元的循证回答，以及用户材料的引用报告和 Markdown 附件。复杂投放复议已交付带 10 个引用的部分回答，仍缺完整履约诊断和采购资格核验；PRD 的重复运行发布门槛尚未达到，完整结果保留在验收记录。

取消 COMPASS_SEARCH_WORKSPACES 和 skillEnabled 对新 Run 的控制。既有工具 catalog、执行审批和预算继续生效。旧 Run 保留协议兼容，用户无需切换搜索模式。

2. 通用 Loop 与工具边界

模型每轮依据观察选择工具、修改查询或提交答案。需要独立子任务时使用既有委派能力：子级按注册元数据继承当前可见的只读查询与检索工具，返回中间结果及证据，父级负责最终交付。

责任方 输入与责任 输出
主模型 用户目标、方法、实际结果和缺口 下一步动作或候选答案
Dispatcher 已注册工具、参数与可信上下文 执行、计量、审批、持久结果
工具／来源服务 当前用户、查询条件与来源版本 鉴权后的结果、空状态或安全错误
Verify 结果适配器、候选与当前任务 观察、证据、接受或继续反馈
发布器 被接受的指定候选修订 正文、引用、修订与发布事件

Run 接受时固定 PromptOps、语义清单与预算。文档工具首次调用时取得可读资料 pin；并发调用共享同一版本，空资料视图也持久固定。每次读取及交付仍由来源服务重验权限。Agent 不维护另一份来源 ACL 或搜索专用工具名单。

无库、无索引文档、无匹配来自获准范围内的真实空状态；定向读取无权引用返回拒绝；权限服务故障返回错误。模型据此选择下一步。正式指标后仍可查明细，工具依据各自契约执行。

通用搜索与交付方法的核心约定 · text / 7 LINES 
1先明确用户需要得到哪些结果。简单任务直接执行；复杂任务维护计划。2依据当前缺口选择工具；用实际返回的实体、时间或线索调整下一问。3候选片段用于定位，结论引用可核对的原文、查询格或计算产物。4遇到空结果、拒绝访问或故障时，依据工具状态调整；记录尚未解决的缺口。5提交 final_answer 前对照用户原问题检查覆盖、依据与冲突。6概念解释、澄清与状态说明使用 plain；依赖资料或数据的事实答复使用 evidence。7收到校验反馈后继续补查或修订；预算不足时缩小答复范围并说明限制。

相同原文或查询记录在工具回执中展示一次，证据条目的 recordRef 指向该记录；服务端保留完整私有证据。

复杂任务可用 todo_write 管理计划。完成待办后仍需对照原问题检查答复。资料正文作为数据进入模型，场景方法与平台约束通过既有 PromptOps 管理。

4. Verify 的通用接入

两个检查点接在已有 accept／dispatch 端口周围。工具目录提供结果适配器，循环保持通用；没有证据适配器的工具仍能运行，其结果先作为观察使用。

检查点 具体工作 怎样继续
after_tool_batch 登记观察、来源、状态与派生关系 把新增事实和缺口装入下一轮
before_delivery 检查格式、任务覆盖、引用、值和结论支持 接受候选，或要求补查、修订、审阅、部分交付

程序检查原文位置、查询格、单位、范围、有限计算、版本与引用归属。目标遗漏、模式选择、解释和建议支持程度，由同一主模型在既有 analyze 阶段执行 purpose=verify 审阅；工具关闭，该调用计入模型预算。Review 与候选摘要和证据修订绑定。

Review 回执持久保存后，由当前 worker 继续完成接受与发布检查；该边界不主动交还租约，减少最后交付前的重放开销。进程中断仍从已保存回执恢复。子任务证据经通用导入端口进入父级账本，保留原 ID 与来源关系。

当前实现对 plain 和 evidence 统一执行同主模型审阅，核对原问题、模式与结论支持。程序核对与模型判断分别记录。

“搜够”由用户目标覆盖、结论依据与未解决冲突共同决定。结果数量与调用次数用于观察成本。无进展时要求调整或缩小答复范围；预算提前预留交付机会，硬耗尽且无合法答案时只展示未完成状态。

5. 普通回答、循证回答与正文边界

final_answer 调用代表提交候选；Verify 接受并提交持久消息后，前端才显示最终正文。 mode 在每次候选中选择，Run 不预选搜索模式。

模式 适用内容 校验和呈现
plain 概念解释、澄清、操作说明、无资料状态 结构检查和同主模型模式／目标审阅；普通 Markdown
evidence 查询数值、企业制度、比较、解释与建议 claims + refs + blocks；程序核值并执行语义审阅；引用角标
partial 两种模式都可声明 明确已完成范围、未解决目标和下一步

依赖企业事实的结论必须满足该任务的依据要求；无法满足时补查、删除相关结论或声明部分完成。完全没有可用事实时，可用 plain 说明状态。

一个普通回答候选 · json / 7 LINES 
1{2  "mode": "plain",3  "completion": "complete",4  "coveredGoalIds": ["root"],5  "unresolved": [],6  "body": "GMV 表示一定口径下的商品交易总额。具体是否扣除退款，需要结合当前业务采用的指标定义。"7}

final_answer 独占工具批次，与其他调用混排时整批在执行前拒绝。调用参数、候选正文和审阅内容保存在私有记录，执行区只显示安全进度。原生工具与结构化输出 Provider 归一到同一候选协议；普通自然文本按执行说明处理。

边界 判断依据
执行 → 候选 注册了完成能力的工具信号，或声明过的结构化答案协议
候选 → 正文 指定修订通过 Verify、当前权限检查和持久发布事务
后端 → 前端 execution nodes 展示过程；已发布助手消息展示正文

正文采用校验后整篇发布，前端可对已接收内容播放打字动画。两个模式共享该边界。子 Agent 只完成自身执行域，根 Agent 接受结果后决定最终交付。

6. 证据、引用与持久化

对象 归属与保存
Observation / Evidence Agent Run 私有记录，含原始定位、范围、版本、状态和派生来源
AnswerCandidate 同 Run 私有记录，含模式、候选修订、正文块和缺口
VerificationRecord 程序结果、主模型 Review、输入摘要、证据修订与决策
PublishedAnswer 最终消息、角标、引用详情、textDigest 与修订
资料、索引与 ACL 现有 Web 知识库或各来源服务；当前权限由所有者执行

模型选择已登记来源，服务端按正文位置生成角标。复用已有引用目录／详情两个 GET 接口和 CitedAnswer 组件。正文、引用与事件在持租事务中一起提交，恢复按 Run、执行域与候选修订去重。

引用详情、历史消息、SSE 回放与派生产物均重验当前访问权。源片段编辑或停用后，旧版本按哈希及状态失效。当前知识库沿用 web/main 既有 0010 迁移，本次候选协议复用 AgentMessage，无新增数据库表。

7. 前端推理接口协议

前端继续使用同一套 Session / Run 接口。新增内容集中在已发布助手消息的回答元数据；证据通过现有引用目录与详情接口传递。 final_answer 是模型在 Runtime 内调用的工具，浏览器提交的内容仍是用户问题。

以下协议已落入 DTO、发布事务与 Web 组件。沿用现有接口路径、compass.run v2 信封和引用 DTO；新增 content.answerMode / completion 明确正文路由与完成范围。接口示例使用虚构制度内容，展示各字段怎样关联。

接口变化一览

前端 HTTP 接口（前缀 /api/web/v1/analysis） 本版变化 传递内容
POST /sessions/submit 请求与 202 回执保持现有结构 问题、模型选择、会话、requestId；无搜索开关，无调用者指定的回答模式
GET /runs/{runId}/events?after=… 保留 event: agent 和 v2 信封；助手消息增加 content.answerMode / completion 过程节点、已发布正文、模式、完成范围、正文摘要

所有浏览器请求沿用登录 Cookie。POST 同时携带同源 Origin、Content-Type: application/json 和 X-CSRF-Token；tenantId / workspaceId 在 POST body 或 GET query 中传入。Web BFF 校验当前身份后构造受信上下文，代理到 Agent 的 /v1/analysis 对应路径；服务凭据只在服务端使用。成功及失败响应均沿用 no-store。

⑤ 普通回答、部分回答与历史回看。 普通回答使用相同的 message.upsert 和 run.upsert；下面只展示其消息 payload，外层信封与上例一致：

普通回答的消息 payload · json / 13 LINES 
1{2  "messageId": "10000000-0000-4000-8000-000000000016",3  "ordinal": 2,4  "role": "assistant",5  "revision": 2,6  "status": "completed",7  "content": {8    "text": "GMV 表示一定时期内的商品交易总额。",9    "artifactIds": [],10    "answerMode": "plain",11      "completion": "complete"12  }13}
公开状态 前端处理
answerMode=plain 以 Markdown 显示正文，跳过引用目录请求
answerMode=evidence 显示正文，匹配目录后生成角标，点击后请求详情
completion=partial 已接受的部分回答；消息与 Run 都可为 completed，正文明确已完成范围、限制及下一步
消息 status=incomplete 沿用运行中断／取消等语义；新协议候选保持私有，执行区显示未完成状态
新协议初始 streaming 空助手消息 仅为占位；执行过程显示在节点区

两种回答模式均支持 partial。正文的完成范围以 completion 表达；传输／运行状态保留各自含义。前端无需按工具名或正文正则选择回答模式。历史 GET 返回 mode=snapshot 的相同 AgentResponse：消息 payload 与实时发布一致，packet.seq 为 null，page 为分页对象，cursors 提供后续订阅位置。

引用目录或详情返回 404 时显示“当前无法查看这条引用”，并刷新当前消息投影；权限不足沿用 403，来源服务暂不可用由 BFF 返回统一 503，界面提供重试。公开错误继续使用现有错误信封，失效细因留在内部记录。引用不可读时，正文、派生结论及产物同步经过来源投影，缓存也随作用域与消息修订清理。
